## 0. Why this relaunch exists

The 2026-08-31 relaunch chain (genesis timestamp `1788172787831`) froze at height 2639.
Root cause, confirmed 2026-09-03: `BlockDiffer.createInitialBlockSnapshot` (miner forge
path) read `blockchain.carryFee(...)` unconditionally, while `BlockDiffer.fromBlockTraced`
(appender recompute path) branches three ways on `stateHeight` vs `ngHeight` vs
`sponsorshipHeight`. Below `sponsorshipHeight` the stored `carry` is structurally 0 while
the appender recomputes a non-zero carry — a systematic, height-gated formula
disagreement. On the live chain `sponsorshipHeight = 3000` (FeeSponsorship pre-activated
at height 0, `feature-check-blocks-period = 3000`), which is why the stall landed just
below 3000. Fixed in `31d4410ba3`, contained in the target image above.

Because the divergent history is frozen into the current chain, the fix cannot be applied
in place — the chain must be re-genesised. That is the whole reason Step 5 (the wipe)
exists.

### 4.3 The arithmetic — why all four

Activation rule: within a rolling window of `feature-check-blocks-period = 3000` blocks, at
least `blocks-for-feature-activation = 2700` blocks must have been produced by nodes voting
yes. That is a **90.0%** ratio.

The chain has **four** nodes, of which **three are forging generators** (main, gen-0,
gen-1) and one (`dcc-val-0`) is a validator. Block production share is what counts — not
node count — so the arithmetic must be done on expected block share.

Assume the three generators share block production roughly evenly (~33.3% each, the design
intent; actual share varies with balance-weighted PoS — main holds 4B vs 2B each for gen-0
and gen-1, so main's real share is higher, roughly 4/8 = 50% with gen-0 and gen-1 at ~25%
each).

| Voting set | Best-case vote share of blocks | ≥ 90%? |
|---|---|---|
| All 3 generators (+ val-0 for good measure) | 100% | ✅ yes, with 10 points of headroom |
| main + gen-0 (gen-1 abstains) | ~75% (4B+2B of 8B) | ❌ no |
| main + gen-1 | ~75% | ❌ no |
| gen-0 + gen-1 (main abstains) | ~50% | ❌ no |
| any single generator | ≤ 50% | ❌ no |

**Conclusion: every block-producing node must vote yes.** With three generators there is
no subset that clears 90% — dropping the *smallest* producer (gen-0 or gen-1, ~25%) still
leaves only ~75%, well short of 90%. There is no "3 of 4 is enough" margin here; the
question does not even arise, because the fourth node (val-0) does not forge, so the
budget is really "3 of 3 generators."

**Consequence for operations, state this to the operator explicitly:** with zero headroom,
**any generator being down for more than 10% of a 3000-block window (>300 blocks, ~2.5h at
a 30s target block time) resets the vote for that window.** Feature 26 will therefore not
activate until the fleet sustains ~3000 blocks (~25 hours) with all three generators
healthy and voting. This is not a failure mode — the window simply rolls — but do not
expect activation to be quick or to survive a mid-window incident. Add `26` to `val-0`'s
`supported` list anyway: it costs nothing, and it makes the vote correct if val-0 is ever
promoted to a generator.

- [ ] Operator has been told, in writing, that feature-26 activation requires ~25h of
      all-generators-healthy uptime and that the reward change does not take effect at
      genesis.

## 12. Step 11 — Post-relaunch evidence plan / 72h soak

### 12.1 72-hour soak with recorded drills

Start the clock only once §8's checks are all green and the chain has passed height 3100.
Record each drill with timestamps, the command run, and the observed recovery — a drill
that happened but was not written down does not close the checklist item.

- [ ] **Crash drill.** Kill one generator pod / stop the VPS container abruptly. Record:
      time to rejoin, whether finalized height regressed (it must not — the HotStuff floor
      is monotonic max()-merge), and whether `lockedQC` reloaded from
      `HotStuffLockedQCStore` (this is T11's mitigation; see 12.3).
- [ ] **Partition drill.** Network-isolate one LKE generator from the other two for >1
      generation period. Record whether the majority side keeps finalizing and whether the
      isolated node rejoins without forking.
- [ ] **Committee-rotation drill.** Observe at least one clean generation-period boundary
      (every 100 blocks) with a *changed* committee membership, and confirm
      `/generators/at/<start>` returns the new set before the boundary.
- [ ] **Equivocation drill.** See 12.4 — this one is staged separately.
- [ ] Zero `InvalidStateHash` occurrences across the full 72h. This is the specific
      regression the relaunch exists to clear.
- [ ] Finalized height (`/blocks/height/finalized`) tracked continuously and never stalls
      for more than `settled-depth` × block time.

### 12.2 Live epoch transition (T10)

**T10** is the cross-committee-epoch fork item in `hotstuff-audit-readiness.md` §4/§7
(table row at `docs/hotstuff-audit-readiness.md:98`): two disjoint committees each forming a
valid 2/3-stake QC for a different block at the identical `(view, height)`. The fix binds
`committeeEpoch` (schema 1.6.5, `dcc/block.proto` field 7) into the signed vote/QC bytes,
derived as a pure function of the *target* height.

The §8 checklist item still open:

> `[ ] Live multi-node Docker evidence of an actual committee-epoch (T10) transition —
> unit/DST-simulation only so far`

- [ ] Observe and record a real committee-epoch transition on the live relaunched chain
      (a generation-period rotation that changes committee membership), with the
      `committeeEpoch` values on votes/QCs either side of the boundary captured from logs.
      This closes a checklist item that simulation alone cannot.

### 12.3 T11 first-boot window — operational rule (plan Decision D5)

**This rule is real, and it applies to this relaunch specifically**, because a wipe-and-
relaunch puts every node back into first-boot state simultaneously.

From `hotstuff-audit-readiness.md:115` (T11): `HotStuffLockedQCStore` persists a replica's
real `lockedQC` to disk on every genuine advance and reloads it at coordinator construction,
closing the replay window from a replica's **second** boot onward. It does **not** close the
window on a replica's **very first-ever boot**, when nothing has been persisted yet. That
one-time gap remains, bounded only by `HotStuffEngine.onQC`'s monotonic commit-height guard.

Decision D5 keeps this as a documented operational rule rather than consensus code.
Operationally, for this relaunch:

- [ ] Treat the period from first boot until each node has persisted its first real
      `lockedQC` as an elevated-risk window. Do not introduce new/untrusted peers during it.
- [ ] Do not perform the equivocation drill (12.4) during the first-boot window.
- [ ] Confirm each of the four nodes has advanced and persisted a `lockedQC` (i.e. has
      completed at least one genuine finalization) before considering the window closed.

### 12.4 One live equivocation exercise — ONE node first

`slashing-enabled` defaults to **off** (`HotStuffSettings.scala:88-90`, plan Decision D4)
and is miner-fold only. The audit checklist records the T5 slashing wiring as done but with
"**live testnet exercise pending** before `slashing-enabled` is turned on anywhere."

- [ ] Set `slashing-enabled = true` on **exactly one** node. Not two. Not all four.

- [ ] Record the full evidence trail (transaction, proof bytes, log lines, resulting
      exclusion).
- [ ] **Only then** decide, as a separate deliberate decision, whether to go fleet-wide.
      Turning it on everywhere before a clean single-node exercise risks slashing honest
      generators on a chain that is 72 hours old.
- [ ] `authoritative` stays advisory (D4 / audit item F-1) — do not change its semantics as
      part of this relaunch.

### 12.5 Feature 26 activation watch

Per §4.3, activation needs ~3000 blocks (~25h) of all-generators-healthy voting, and any
generator down for >~300 blocks in a window resets it.

- [ ] Poll `/activation/status` daily; track feature 26's `blockchainStatus` progression
