## Deployment Architecture

### Layer 0 — GitHub org secrets and variables

Global credentials shared by deploy, publish, release, and CI workflows in the `Decentral-America` org.

### Layer 1 — Infra repo secrets and environments

Provisioning credentials plus per-network SSH deploy credentials scoped to `Ecosystem/infra`.

### Layer 2 — On-server secrets

`/opt/dcc/secrets/<network>.env` written once by Linode bootstrap. Never committed. Used by containers at runtime.

### Layer 3 — Compose runtime constants

Non-secret values layered on top of `env_file:` for container ports, startup behavior, and health checks.

### Layer 4 — App build-time environment

Checked-in app `.env.*` files and CI-injected build arguments such as `SENTRY_RELEASE`.

### Layer 5 — OpenTofu input/output/state

Provisioning inputs, outputs, and remote state backend configuration.

### Layer 6 — Workflow-to-secret cross-reference

Every workflow mapped to the secrets and variables it consumes.

### Layer 7 — Container supply chain

Pinned base images used by Docker builds in launch-critical services.

### SOPS + age secrets — encryption key management

All sensitive secrets are SOPS-encrypted with age keys before committing to git. Each environment has its own age key pair stored in GitHub Secrets.

| GitHub Secret | Environment | Purpose |
|---|---|---|
| `AGE_KEY_testnet` | infra/testnet env | SOPS decryption key for `secrets/testnet.env` |
| `AGE_KEY_stagenet` | infra/stagenet env | SOPS decryption key for `secrets/stagenet.env` |
| `AGE_KEY_mainnet` | infra/mainnet env | SOPS decryption key for `secrets/mainnet.env` |

**Post-quantum upgrade (recommended, one-time, free):**
age v1.3.1 supports hybrid ML-KEM-768 + X25519 keys (`age1pq1...` format, NIST FIPS 203). The existing X25519 keys are vulnerable to harvest-now-decrypt-later quantum attacks. To migrate:

```bash
# 1. Generate new PQ keys (do this OFFLINE or on a trusted machine)
age-keygen -pq -o ~/.config/sops/age/keys-pq-testnet.txt   # save AGE-SECRET-KEY-PQ-1... to KeeWeb
age-keygen -pq -o ~/.config/sops/age/keys-pq-stagenet.txt
age-keygen -pq -o ~/.config/sops/age/keys-pq-mainnet.txt

# 2. Re-encrypt each secrets file (adds new recipient, removes old)
cd Ecosystem/infra
SOPS_AGE_KEY_FILE=~/.config/sops/age/keys-pq-testnet.txt \
  sops rotate \
  --add-age age1pq1<TESTNET_NEW_PQ_PUBLIC_KEY> \
  --rm-age age1gpe6clrwzvfjlkwm2ww4a00f0ktk49raaslgs2zr3r0vzkcez9fsd97vzs \
  secrets/testnet.env
# Repeat for stagenet and mainnet

# 3. Update .sops.yaml with new age1pq1... recipients

# 4. Update GitHub Secrets AGE_KEY_* with new AGE-SECRET-KEY-PQ-1... values

# 5. push-secrets.yml already uses SOPS v3.13.1 which supports PQ keys
```

## Enterprise Launch Plan

> Detailed owner and ticket sequencing lives in [../STATUS.md](../STATUS.md#backend-launch-execution-plan). This section is the deployment-side operating model that those workstreams execute against.

### Research-backed execution rules

| Source | Verified rule | Operating implication |
|---|---|---|
| [GitHub reusable workflows](https://docs.github.com/en/actions/sharing-automations/reusing-workflows) | `workflow_call` is the supported reusable deployment surface, and a called job's `environment` uses that repo's environment secrets. | Node and matcher deploys should reuse the infra deploy workflow or the same environment ownership model; do not duplicate `DEPLOY_*` across repos. |
| [GitHub environments](https://docs.github.com/en/actions/deployment/targeting-different-environments/using-environments-for-deployment) | Reviewers, wait timers, branch restrictions, and secrets are enforced at the environment layer. | `mainnet` approval must be implemented as an environment control, not a convention. |
| [GitHub concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) | Shared deploy targets require a concurrency group; production deploys should serialize and must not cancel in flight. | Each rollout path should serialize by `service + network`. |
| [Docker Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/) | Compose waits for running state, not true readiness, unless `healthcheck` and `service_healthy` are defined. | `--wait` is necessary but not sufficient for node, matcher, PostgreSQL, BPS, or data-service readiness. |

### Review outcome

### Key Rules

1. **Maven before npm.** JVM crypto primitives (curve25519, blst, groth16) are foundational. npm packages that wrap them (e.g., `@dcc/crypto` via wasm-pack) are built separately but consume the same algorithms.
2. **Node before Matcher.** The matcher declares `node % Provided` — it compiles against the node-scala JAR but doesn't bundle it. The node must be published first so the matcher's CI can resolve it.
3. **SDK before Apps.** All five apps import from `@decentralchain/*` SDK packages. If you bump an SDK package, rebuild and publish it before deploying apps.
4. **Infra is independent.** OpenTofu provisioning and Docker Compose deploys don't depend on any artifact — they pull published Docker images. Run infra provisioning whenever you're ready.
5. **Never skip tiers.** A Tier 3 publish that references a Tier 0 artifact that hasn't been published yet will fail with "Could not resolve io.decentralchain:curve25519".
