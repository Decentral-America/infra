## BLOCKER

### F-01 BLOCKER: Browsers block every matcher call (duplicate `Access-Control-Allow-Origin`), so DEX trading on the exchange and the scanner's DEX Pairs page are dead
- Evidence: `curl -H 'Origin: https://testnet.decentral.exchange' https://testnet-matcher.decentralchain.io/matcher/settings` (also `/matcher`, `/matcher/orderbook`) returns two headers: `access-control-allow-origin: https://testnet.decentral.exchange` AND `access-control-allow-origin: *`. The upstream matcher on its own (`curl localhost:6886` on the VPS) sends `Access-Control-Allow-Origin: *`. The `testnet-matcher.decentralchain.io` block in the live Caddyfile (`/opt/dcc/caddy/Caddyfile`, generated by infra `update-caddy.yml`, mtime 2026-10-10) adds the reflected origin with `header @cors_allowed_origin …` and has no `header_down -Access-Control-Allow-Origin` in its `reverse_proxy` (only the ipinfo proxy has one). The node block sends a single header, so the node is fine.
- Headless Chrome confirmation: on `https://testnet.decentral.exchange/desktop/dex` and `/desktop/swap` the console shows `Access to fetch at 'https://testnet-matcher.decentralchain.io/matcher/settings' … blocked by CORS policy: The 'Access-Control-Allow-Origin' header contains multiple values`. On `https://testnet.decentralscan.com/dexpairs` the matcher `/matcher/orderbook` call fails the same way and the page shows "Total Pairs 0 / No trading pairs available", with no error shown to the user.
- Why it matters: the exchange cannot load matcher settings, the order book or pairs, and cannot place or cancel orders from any browser. The node-based E2E suites skip browser CORS, so they stay green while the DEX is broken for real users.
- Fix (infra, `update-caddy.yml` matcher block): add `header_down -Access-Control-Allow-Origin` (and `-Access-Control-Allow-Credentials`) inside the matcher `reverse_proxy`, or drop Caddy's ACAO for that host. Then add a browser-level CORS smoke check (see F-19).

## HIGH

### F-02 HIGH: The exchange's only configured testnet trading pair points to an asset that no longer exists
- Evidence: `apps/exchange/src/configs/testnet.json` `tradingPairs: [["C84Qs2JfpDKwCrwqByj4YNwxXQfLqQCBvYboKQMv6yB6","DCC"]]` (commit `c21b45c75`, 2026-06-16, "DCC/CRC pair now live"). The node returns `{"error":313,"message":"Asset does not exist: C84Qs2…"}`, the matcher returns 404 `The asset C84Qs2… not found`, and data-service `/v0/pairs/C84Qs2…/DCC` returns HTTP 500. `features/dex/tradingPairs.ts` builds `AVAILABLE_PAIRS`/`DEFAULT_PAIR` only from this config, and MarketsPanel, MarketSearchDialog and Dex.tsx all read it. The matcher's 22 real markets are never listed.
- Why it matters: even after F-01 is fixed, the DEX opens on a pair that does not exist (probably wiped by the chain re-genesis), and users cannot reach any real market from the UI.
- Fix: replace with a real testnet asset pair, or better, derive the market list from `GET /matcher/orderbook` filtered by an allowlist. Add a CI or deploy check that every configured asset id exists on the target node.

### F-03 HIGH: The testnet exchange's Swap (AMM) tab is wired to MAINNET
- Evidence: `apps/exchange/src/config/amm.ts` hardcodes `AMM_NODE_URL='https://mainnet-node.decentralchain.io'`, `AMM_CHAIN_ID='?'`, PoolCore `3DcZHm89…` and Router `3Dc9mKvi…` (mainnet addresses). `services/amm/indexer.ts` hardcodes `https://amm-indexer-production.up.railway.app`. There is no network gate like `BRIDGE_SUPPORTED` in `config/bridge.ts`. The live testnet bundle contains `Ae="https://mainnet-node.decentralchain.io"` with `new De({chainId:"?",dAppAddress:Oe,…})`. Swap is in `TOP_TABS` (`layouts/shell/navigation.tsx`). The testnet node reports `addresses/validate/3DcZHm89…` → `valid:false`.
- Why it matters: testnet users see mainnet pools, prices and TVL as if they were testnet. Swaps are signed by the app's testnet signer and broadcast to the testnet node against a mainnet dApp address, so they fail, and then `confirmApplied` polls the mainnet node for a testnet tx id until it times out. The feature is misleading and broken.
- Fix: put AMM config into the per-network JSON. Hide Swap, the same way the bridge is hidden, on networks with no AMM deployment.

### F-04 HIGH: The live exchange (Cloudflare Pages) sends no CSP, HSTS or frame-ancestors/X-Frame-Options, and the prior audit's "exchange has CSP" claim is wrong
- Evidence: the live response headers for `https://testnet.decentral.exchange/` contain only `referrer-policy`, `x-content-type-options` and `cache-control`. They have no `content-security-policy`, `strict-transport-security` or `x-frame-options`. The deployed header file `apps/exchange/public/_headers` defines only those three. The thorough CSP lives in `apps/exchange/nginx.conf` / `docker/nginx/default.conf`, but deploy-exchange.yml uploads `dist/` straight to CF Pages, so nginx is never in the path. `index.html` says "CSP is configured via Vite server headers in vite.config.ts", which only covers the dev server. `src/lib/tokenLogos/__tests__/csp.test.ts` checks the CSP in three files that never ship. AUDIT-REPORT.md item 0b says the exchange "has a real, thorough CSP already, applied via apps/exchange/nginx.conf at the production reverse-proxy layer", which is false for the CF deployment.
- Why it matters: this is a non-custodial wallet that holds encrypted seeds in browser storage and signs transactions. It can be framed, so clickjacking against sign or approve flows is possible. Nothing limits XSS or the third-party script surface (GA loader, TradingView, jsDelivr), and there is no HSTS.
- Fix: put the nginx CSP (plus `frame-ancestors 'none'`, HSTS and X-Frame-Options) into `public/_headers`. Point csp.test.ts at `_headers`, the file that actually ships.

### F-05 HIGH: The exchange's "Install Cubensis Connect" button sends users to Waves' Keeper Wallet
- Evidence: `apps/exchange/src/pages/CubensisConnectImportPage/CubensisConnectImportPage.tsx:211` has `href="https://chrome.google.com/webstore/detail/decentralchain-keeper/lpilbniiabackdjcionkobglmddfbcjo"`. That id resolves (HTTP 200) to `chromewebstore.google.com/detail/keeper-wallet/lpilbniiabackdjcionkobglmddfbcjo`, titled "Keeper Wallet - Chrome Web Store". The same link is in the live bundle and in several locale files. Cubensis has never been published (F-15).
- Why it matters: users are told to install a different vendor's wallet. It does not inject `window.CubensisConnect` (see `lib/data-service/classes/Seed.ts:27`), so the flow cannot work, and it pushes users toward custody by a third party.
- Fix: remove the button until Cubensis has a real store listing, then link to that listing.

### F-06 HIGH: The explorer shows wrong amounts and the wrong asset for every non-DCC transaction
- Evidence: in `apps/scanner/src/pages/Transaction.tsx:321-325`, `{formatAmount(displayTx.amount)} DCC` is applied whatever the tx's `assetId` is. Live check: tx `aXKyqAVx9EDCZceT77YA9q15JQNVyrnegkCPkGvZcSm` (Burn, block 73276) burns `amount 10000000` of asset `9P2QmU7s…` (AUDT, 2 decimals, i.e. 100,000 AUDT). The scanner renders "Amount 0.1 DCC".
- Why it matters: an explorer's core job is showing correct amounts. Transfers, burns, issues and reissues of any token are misreported, both in value (off by a factor of 10^(8−decimals)) and in asset.
- Fix: resolve the asset's decimals and ticker (the scanner already calls asset details) and format with them. Add a test using a non-8-decimal asset.

### F-07 HIGH: Deployed scanner and admin-dashboard images run dependency versions with known advisories that main already patched
- Evidence: `docker exec scanner-testnet ls /app/node_modules/.pnpm` and the same for `admin-dashboard-testnet` show `compression@1.8.1` and `proxy-addr@2.0.7`. Commit `645813e50` (2026-10-07) pins `proxy-addr >=2.0.8` (GHSA-jqcg-44mw-7w3h, critical) and `compression >=1.8.2` (GHSA-vc2v-76pw-4v95, high, memory-leak DoS). Both servers are `react-router-serve` (express plus compression) and face the internet. `pnpm audit --prod` on main is clean apart from the documented braces ignore. The last deploys were 2026-08-16 (see the table).
- Why it matters: the public scanner and admin servers carry a remotely triggerable DoS that is already fixed in source. The only thing missing is a redeploy.
- Fix: redeploy scanner and admin-dashboard from current main via `deploy-*.yml` workflow_dispatch (network=testnet). Consider a scheduled Trivy scan of running image digests.

### F-08 HIGH: The public scanner container, and the admin container, receive the entire network secrets file
- Evidence: `docker inspect scanner-testnet` lists 48 env vars, including `MATCHER_ACCOUNT_SEED`, `MATCHER_ACCOUNT_PASSWORD`, `DCC_WALLET_SEED`, `DCC_CANARY_SEED`, `NODE_REST_API_KEY`, `MAIN_NODE_REST_API_KEY`, `ADMIN_DASHBOARD_GITHUB_PAT`, `ADMIN_DASHBOARD_GITHUB_OAUTH_CLIENT_SECRET`, `ADMIN_DASHBOARD_JWT_SECRET`, `SENTRY_AUTH_TOKEN`, `PGPASSWORD`/`POSTGRES__PASSWORD`, `REDIS_URL` with an inline password, and `REPO__PASSWORD`. The scanner needs only about `DCC_FAUCET_SEED`, `DCC_NODE_URL`, `DCC_CHAIN_ID`, `DCC_FAUCET_*`, `REDIS_URL` and `DCC_DATA_SERVICE_URL`/`DCC_MATCHER_URL`. Both containers use `NetworkMode=host`. The admin container gets the same superset, including faucet and matcher seeds it does not use.
- Why it matters: least-privilege is broken. Any SSR bug, SSRF, dependency compromise (see F-07) or log leak in the public explorer exposes the admin JWT signing key (which allows forging admin sessions), the GitHub PAT and OAuth secret, the node API key and the matcher seed. Testnet seeds are accepted as public, but GitHub, Sentry and JWT credentials are not testnet-scoped.
- Fix (infra `deploy-container.yml`/bootstrap): give each service its own env file with only the variables it needs. Rotate the JWT secret, GitHub PAT and OAuth secret after the split.

### F-09 HIGH: Anonymous internet access to Grafana, including arbitrary Loki log queries over every container
- Evidence: `GET https://grafana.testnet.decentralchain.io/api/frontend/settings` returns `anonymousEnabled: true` (Grafana 13.2.3). Without credentials, `/api/search` lists dashboards, `/api/datasources/uid/loki/resources/label/container/values` lists 16 containers (caddy, matcher, node-scala, admin-dashboard, scanner, data-service, …), and `POST /api/ds/query` with a Loki expr returned real log lines (40 values in 15 minutes) and caddy access logs (which hold every visitor's IP, user agent and URI). A spot check found Authorization headers redacted in caddy logs, and no plaintext X-Api-Key was found. No `X-Frame-Options`/`frame-ancestors`, so any site can frame it. The admin-dashboard embeds this Grafana (`frame-src https://grafana.testnet.decentralchain.io` in the admin CSP), which suggests anonymous access was enabled to make the embed work.
- Why it matters: anyone can query public log search of every service, including user IPs (PII), internal errors and admin activity. Other infra auditors may also report this; it is listed here because it backs an admin-dashboard feature.
- Fix: turn off anonymous access, or limit anonymous users to a dedicated org with only public dashboards and no Loki datasource. Put Grafana behind the admin's GitHub-OAuth (auth proxy) for the embed. Set `frame-ancestors https://testnet-admin.decentralchain.io`.

## MEDIUM

### F-10 MEDIUM: The explorer labels the block signature as "Block ID", and searching for that value returns 404

For v5 blocks, id ≠ signature: at height 73276 the node reports id `2LwvykyqKufc…` and signature `2Zuv71Qkc3…`. Live `blockdetail?id=<signature>` shows "404 Block Not Found", and node `/blocks/<signature>` returns 404. Nowhere in the explorer shows the real block id.

### F-11 MEDIUM: The block detail page shows raw base units ("Reward 2000000000 DCC", "Fee: 100000")
- Evidence: live `blockdetail?height=73276` shows "Reward 2000000000 DCC" (20 DCC; the dashboard correctly shows "20 DCC") and the transaction rows show "Fee: 100000".
- Fix: apply `formatAmount` there as other pages do.

### F-12 MEDIUM: The faucet's bot protection does not work and its per-address limit can be raced
- Evidence: `apps/scanner/src/routes/api.faucet.ts` verifies reCAPTCHA only when `DCC_RECAPTCHA_SECRET` is set, but `pages/Faucet.tsx:44` never sends `captchaToken`, so turning the secret on would break the faucet. The live container has no `DCC_RECAPTCHA_SECRET`. The per-address limit is check-then-set: `isRateLimited()` uses GET, then broadcast, then `recordRequest()` SET only after broadcast, so concurrent POSTs for one address all pass. What exists: the Caddy edge limit of 5 req/h/IP (`zone faucet_per_ip`), Redis-backed per-address 24h (`REDIS_URL` set), chain-id check (`DCC_CHAIN_ID=33`), 10 DCC per request. Nothing monitors the faucet balance (no faucet or balance metric in Prometheus; `dcc_service_up{service="faucet"} 1` is just a liveness ping).
- Why it matters: with many IPs (IPv6 or proxies) an attacker can drain the faucet at 50 DCC/h per IP with no captcha, and nobody is alerted when it runs dry. That happened once before (it was re-funded after the re-genesis).
- Fix: reserve atomically with `SET key NX PX` before broadcasting and release on failure. Either wire the reCAPTCHA (or Turnstile) client token or delete the dead path. Add a balance gauge and alert.

### F-13 MEDIUM: The matcher market list is full of E2E leftovers
- Evidence: `GET /matcher/orderbook` lists 22 markets. 21 are `E2ETestTkn/DCC`, plus one `DEXPROOF/DCC`. All sampled order books are empty.
- Why it matters: once F-01 and F-02 are fixed, testnet users browsing markets on the scanner or exchange will see only junk test tokens.
- Fix: have E2E clean up (cancel orders, and delete the orderbook through the matcher admin API) or use a dedicated matcher. Have the UIs show only allowlisted pairs.

### F-14 MEDIUM: The admin-dashboard Treasury "fund" action is disabled in production by missing config
- Evidence: `routes/api.treasury.fund.ts` `isAllowedNodeUrl()` returns false when `ADMIN_DASHBOARD_ALLOWED_NODE_URLS` is empty and `NODE_ENV=production`. The live container has `NODE_ENV=production` and no such variable. It also has no `TREASURY_SEED`, so every fund or sweep needs a seed pasted into the browser (`LoadTest.tsx:363`).
- Fix: set `ADMIN_DASHBOARD_ALLOWED_NODE_URLS=https://testnet-node.decentralchain.io` and a dedicated `TREASURY_SEED` in the admin env file only (see F-08).

### F-15 MEDIUM: Cubensis Connect has never been released, and nothing is in place to release it

None of the required `CHROME_*`, `FIREFOX_*` or `EDGE_*` secrets exist at repo, org or any environment level (environments: mainnet, maven-central-release, npm-release, preview, production, testnet). `apps/cubensis-connect/INFRA-READINESS-CHECKLIST.md` still lists open blockers (E2E fixtures, canonical origins).
- Why it matters: the testnet has no installable DCC wallet extension, and the exchange's Cubensis login and import path cannot be used (see F-05).

### F-17 MEDIUM: Every transaction link in the scanner's public Stress page goes to a dead host

### F-18 MEDIUM: i18n gaps. The scanner renders raw keys; the exchange's new surfaces skip i18n
- Scanner: `components/utils/translations.tsx` defines en (258 keys) and es (265), but 52 keys passed to `t()` are missing in both (for example `balances`, `nfts`, `leases`, `addressCopied`, `blockSize`, `failedToLoadTransaction`). `t()` falls back to the key, and the live Address page shows the tabs "balances … nfts leases".

### F-19 MEDIUM: No post-deploy browser smoke test, so the CORS break and the dead default pair were never caught

### F-20 MEDIUM: load-tester's own test suite is red on main, and no CI builds or tests it

### F-21 MEDIUM: admin-dashboard has almost no test coverage on security-critical code
